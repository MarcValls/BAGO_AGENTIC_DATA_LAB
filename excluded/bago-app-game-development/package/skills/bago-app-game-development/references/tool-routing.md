# Tool and integration routing

Use this reference when choosing tools, optional skills, engines, MCP servers, or project utilities.

1. Inspect the capabilities available in the current session: installed skills, callable tools, repository scripts, local SDKs, and permitted browser/simulator/runtime surfaces.
2. Match a capability to the task. Prefer the narrowest tool that can produce direct evidence for the requested boundary.
3. Treat a manifest, README, MCP tool name, plugin source, or agent definition as a candidate description, not proof that it is installed, loaded, current, safe, or exercised.
4. Before an external or material effect, confirm the exact target and current authorization. Tool visibility is not permission to publish, deploy, spend money, modify accounts, delete data, or send messages.
5. If a specialized capability is absent, use source-level or local alternatives and clearly state what runtime evidence is unavailable. Do not simulate a tool result.

Examples of optional capability classes include browser automation for web flows, accessibility inspection, iOS/Android simulators, engine editors/CLI exporters, asset generation, and platform signing tools. Resolve their actual names and availability from the current environment rather than hard-coding a dependency on another harness.
